# EasyR1 接入、attention mask 修复与 one-step GRPO 调试记录

日期：2026-08-08  
工作分支：`codex/latent-step-reward`

## 1. 本轮目标

将 OneThinker 的 EasyR1 固定版本以 vendored 方式接入 CoLT，并使其能够：

- 使用 CoLT 的 `latent_reasoning_generate` 完成 rollout；
- 对 hidden latent reasoning 条件下的可见 response 计算策略 log-prob；
- 使用 CoLT 兼容的 outcome reward；
- 在固定参数时保证 rollout old log-prob 与 actor 重算 log-prob 一致；
- 在独立 `colt-easyr1` Conda 环境中完成真实 one-step GRPO。

## 2. 主要改动

### 2.1 EasyR1 本地化与训练入口

- 固定上游 EasyR1 提交 `4a36ad286d04382fce9816ac4429e650157a5f11` 导入为仓库内 `EasyR1/`。
- 脚本默认 EasyR1 路径改为 `$REPO_ROOT/EasyR1`，不再依赖外部 OneThinker 工作区。
- 新增 CoLT 固定 v2 的 GRPO 配置、预检、RL 命令入口与环境依赖清单。

### 2.2 CoLT rollout 与 reward

- 新增 `CoLTTransformersRollout`，直接调用 CoLT 的 `latent_reasoning_generate`，不经 vLLM。
- rollout 生成完成后，对完整 batch 进行 teacher-forced response 打分，写入 `rollout_log_probs`；该路径与 actor 的 latent-conditioned response log-prob 使用同一语义。
- 增加 CoLT-compatible outcome reward：支持 bare answer 与 `<answer>...</answer>`，并将最终 reward 写到有效 response 的最后一个 token。
- latent 模式 prompt 不再要求模型输出可见 `<think>`；visible 模式仍保留原行为。

### 2.3 attention mask 与 left-padding 修复

根因：EasyR1 对 prompt 做 left-padding；CoLT 在带 KV cache 的 latent transition / response decode 中曾只传入当前 token 的 mask，导致历史 padding 不再被屏蔽。rollout 和 actor 因此可能看到不同上下文。

修复：

- 在 Qwen3-VL CoLT 实现中加入 cached attention mask 扩展辅助函数：保留完整 prompt mask，再为 latent cache 与当前 response token 追加有效位。
- 应用于 latent reasoning forward、latent-conditioned response forward 与 `latent_reasoning_generate`。
- rollout 保留原始 left-padded prompt/attention mask，不再去 padding；batch scorer 的 mRoPE position 维度与 actor 完全对齐。
- `latent_to_decoder_scale`、`alpha` 改为一维参数，绕开 FSDP 对 0-D parameter 的限制；加载时自动把 fixed-v2 checkpoint 的旧标量权重 reshape 为一维。

## 3. 调试过程与结论

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| left-padding 下 rollout 与 actor log-prob 可能偏离 | cached forward 丢失完整历史 attention mask | 完整 mask 传播 + left-padding 回归测试 |
| FSDP 初始化失败 | CoLT checkpoint 中两个可训练标量为 0-D tensor | 参数改为 `[1]`，兼容加载旧 checkpoint |

### 精度结论与下一步

- parity 不比较优化器状态；它发生在 `optimizer.step()` 之前，优化器状态不能解释当前冻结策略的前向差异。

## 8. 2026-08-09 parity 闭环、真实 8 GPU smoke 与全量任务更新

> 本节记录第 7 节之后的实际进展。第 7 节保留了 parity 尚未通过时的中间状态，不能与本节最终结论混读。经过分层诊断、代码修正和真实图像数据验证，rollout old log-prob 与 actor 重算 log-prob 已通过 parity；随后已经启动全量 image-only Outcome-GRPO。本文档记录的是证据快照，不把正在运行的全量任务提前描述为已经训练完成。

### 8.1 最终验收标准

本轮把“训推一致”拆成四个可独立检查的条件：

1. **数学对象一致**：rollout 生成的同一条 response token 序列，在相同的 latent state、图像输入、attention mask、mRoPE position ids 和 temperature 下，由 rollout 与 actor 分别计算 response token log-prob。
2. **有效 token 一致**：parity 只比较第一个 EOS 之前的有效 response token，不把 EOS 后 padding 的任意 logits 当成训练信号。
3. **真实多卡 smoke**：使用真实 image-only 数据、8 张物理 A100、`n=4` rollout、2 个训练 step，训练进程正常返回，不靠 Ctrl-C 或异常退出结束。
4. **全量任务启动**：smoke 通过后启动完整 image-only manifest 的后台训练，并保留启动命令、配置、进程、GPU、Ray 和日志证据。

当前 parity gate 的正式阈值是有效 token 最大绝对误差 `<= 0.05`。这个阈值是故障拦截条件，不是最终数值精度目标；最终 smoke 和全量任务实际达到约 `1e-6` 量级。

### 8.2 训推 log-prob mismatch 的分层诊断

#### 8.2.1 先固定 rollout 与 actor 比较的语义

CoLT 的 latent RL 路径不是普通的“把可见 `<think>` 文本喂给 actor”。每个样本的实际路径是：

```text
图像 + prompt
    -> latent_reasoning_generate
    -> hidden latent state + sampled response token ids
    -> latent-conditioned teacher-forced scoring
    -> rollout_log_probs

同一批 input_ids / response_ids / response_mask / position_ids / image
    -> FSDP actor compute_log_probs
    -> old_log_probs
```

rollout 侧首先生成 response token，然后构造完整的 `sequence_ids = [prompt, response]`。prompt 保持 left-padding；attention mask 保留完整 prompt mask，并在 response 位置追加有效位；mRoPE 的 `position_ids` 也按 response 长度继续扩展。随后 rollout 模型在 latent state 条件下进行 teacher-forced forward，执行：

```python
policy_logits = logits.float() / temperature
log_probs = torch.log_softmax(policy_logits, dim=-1)
token_log_probs = log_probs.gather(dim=-1, index=response_ids)
```

actor 侧使用相同的 CoLT latent response forward 语义重算 `old_log_probs`。训练器在 actor update 之前，用 `response_mask` 过滤有效 token，再计算最大绝对差；超过阈值立即抛错，不允许带着错误的 old log-prob 进入 PPO/GRPO 更新。

#### 8.2.2 失败轨迹与每一步排除的假设

| 阶段 | 关键配置或观测 | 最大差异/诊断 | 结论 |
| --- | --- | ---: | --- |
| 初始 image smoke | rollout 使用普通 batch scorer | `0.366386` | 基础链路能运行，但 rollout 与 actor 数值不一致 |
| 第一轮分层诊断 | rollout batch 16；actor dynamic batching；`use_orig_params=false`；buffer FP32 | `sync_state_max_abs_diff=0.0`；`stored_vs_local_rollout=0.247101`；`actor_vs_local_rollout=1.86103`；`actor_vs_stored_rollout=2.10813` | 权重同步不是根因；存储的 rollout score 与 actor score 同时存在差异 |
| rollout 精度调整后 | rollout/actor 都显式使用 BF16 | `0.670174` | FP32/BF16 不一致确实会影响数值，但单独改 dtype 不能解决问题 |
| 逐样本诊断 | rollout 存储 score 与本地逐样本 score 已一致；actor 仍 dynamic batching | rank 5/6 观测 `batch=(8,4608)`，`stored_vs_local_rollout=0`，`actor_vs_local_rollout=0.287995/0.274567` | mismatch 已收缩到 actor recompute 的 batch 形状/执行路径 |
| `use_orig_params=true` + BF16 buffer | FSDP 参数组织和 buffer dtype 调整，但 actor dynamic batching 仍未完全关闭 | `0.245576` | 这些设置有助于稳定 FSDP 行为和内存，但不是单独的充分条件 |
| 最终修复 | rollout batch-1 逐样本打分；actor dynamic batching=false；experience/update microbatch=1 | Step 1 `2.4959445e-6`；Step 2 `2.6747584e-6` | parity 通过，且真实 image 8-GPU smoke 正常结束 |

最关键的证据是：

- actor 参数同步到 inference/rollout 模型的最大绝对差为 `0.0`，因此不能把主要问题归因于 Ray/FSDP 权重没有同步。
- 逐样本诊断中 `stored_vs_local_rollout=0`，说明 rollout 存储逻辑、response 顺序和 EOS mask 已经对齐。
- 同一时期 actor 的 batch 形状是 `(8,4608)`，而最终 actor experience microbatch 固定为 1；这解释了为什么“参数相同”仍然会有约 `0.27` 的 log-prob 差异。
- 在当前 Qwen3-VL + FlashAttention 路径下，latent-conditioned forward 对 batch shape 不是数值等价的。这里的表述是基于本项目的实测，不把它泛化成所有 Transformer/FlashAttention 实现都必然如此。

#### 8.2.3 为什么不是其他常见原因

- **不是采样随机性本身**：parity 比较的是已经生成并固定保存的 token，而不是重新采样两次。采样 RNG 只影响 token 轨迹，不解释固定 token 上约 `0.2` 到 `2.1` 的 logits 差异。
- **不是 response 顺序错位**：`n=4` 使用 interleave/repeat-interleave 对齐；最终 8-GPU smoke 连续两步通过，说明顺序契约在图像 batch 上成立。
- **不是 temperature 漏传**：rollout 和 actor 均按配置中的 `temperature=1.0` 计算；parity gate 比较的是同一 temperature 下的 response log-prob。
- **不是 EOS 后 padding**：gate 只索引 `response_mask` 有效位置；没有用 padding token 的 logits 掩盖问题。
- **不是优化器状态**：parity 发生在 `optimizer.step()` 之前，优化器动量、二阶矩和 Kahan buffer 不能解释第一次 old log-prob 重算的差异。
- **不是标准 gradient checkpointing 的简单开关**：CoLT latent recurrence 依赖 KV cache，EasyR1 原有标准 checkpoint 路径不能直接套用；因此没有用一个会破坏 cache 语义的 fallback 来掩盖问题。

### 8.3 为解决 parity 做出的代码修改

#### 8.3.1 rollout 改为逐样本 batch-1 teacher-forced scoring

文件：`EasyR1/verl/workers/rollout/colt_transformers_rollout.py`

旧路径把一个 rollout batch 直接送入 inference model 计算全部 `rollout_log_probs`。新路径在保持样本顺序的前提下，对每一条样本执行：

```python
for row in range(sequence_ids.shape[0]):
    row_sequence = sequence_ids[row : row + 1]
    row_attention_mask = attention_mask[row : row + 1]
    row_position_ids = position_ids[row : row + 1]
    row_multi_modal_data = repeated_multi_modal_data[row : row + 1]
    row_logits = inference_model(...)
    row_log_probs = log_softmax(row_logits.float() / temperature).gather(...)
```

具体保持了以下不变量：

- `input_ids`、`attention_mask`、`position_ids`、`response_ids` 和多模态输入使用同一个 row 切片；
- 3-D mRoPE position ids 在送入模型前仍按当前 Transformers 接口转置；
- 每一行结果回到原始设备，再按原顺序 `torch.cat`；
- `rollout_log_probs` 的 shape 和 response batch shape 不变，因此下游 reward、advantage 和 PPO/GRPO 数据契约不变。

代价是 rollout old-log-prob scoring 的 forward 次数增加，吞吐会低于一个 batch forward。这是本阶段为正确性采用的保守实现；在证明 batch-shape invariant 或实现等价的固定 microbatch scorer 之前，不应为了吞吐重新打开普通动态合批。

#### 8.3.2 actor FSDP 配置与 microbatch 形状对齐

文件：`EasyR1/examples/colt_fixed_v2_outcome_grpo.yaml`

最终 actor 关键设置：

```yaml
worker:
  actor:
    global_batch_size: 16
    micro_batch_size_per_device_for_update: 1
    micro_batch_size_per_device_for_experience: 1
    dynamic_batching: false
    model:
      enable_gradient_checkpointing: false
    fsdp:
      enable_full_shard: true
      enable_cpu_offload: false
      enable_rank0_init: true
      use_orig_params: true
      torch_dtype: bf16
      mp_buffer_dtype: bf16
```

其中：

- `dynamic_batching=false` 是对 parity 最关键的执行路径约束，避免 actor 把多个样本按 token 数重新拼成 `(8,4608)` 一类的动态 batch；
- experience/update microbatch 都是 1，使 actor 重算和 rollout 逐样本 scoring 使用相同的 batch shape；
- `use_orig_params=true` 保持 FSDP 参数视图更稳定，便于 actor、unwrapped forward 和同步路径对齐；
- `torch_dtype=bf16` 与 `mp_buffer_dtype=bf16` 减少 rollout、actor 和 FSDP buffer 的 dtype 分叉；这两个设置是稳定性辅助，不应单独被描述为 mismatch 的唯一根因；
- 保持标准 `enable_gradient_checkpointing=false`，因为 CoLT 的 latent recurrence 需要保留可用 KV cache。

#### 8.3.3 增加训练前 parity gate

文件：`EasyR1/verl/trainer/ray_trainer.py`

训练器在 `compute_log_probs(batch)` 之后、actor update 之前执行：

1. 读取 rollout 已保存的 `rollout_log_probs` 和 actor 重算的 `old_log_probs`；
2. 使用 `response_mask` 选取有效 token；
3. 拒绝没有有效 response token 的样本；
4. 拒绝 NaN/Inf；
5. 记录 `policy/rollout_logprob_max_abs_diff`；
6. 超过 `0.05` 立即抛出异常，不进入 actor update。

这使“训练能跑”与“old policy log-prob 语义正确”分离开来，避免错误的 rollout score 静默污染 GRPO 更新。

#### 8.3.4 修复 smoke 结束阶段的验证、保存和 Ray 清理行为

文件：`EasyR1/verl/trainer/ray_trainer.py`、`EasyR1/verl/trainer/main.py`

- `val_freq <= 0` 时不再无条件执行 final validation。当前 smoke/full run 使用 `val_freq=-1`，因此不会在训练结束时意外加载同一份大图像数据做验证。
- `save_freq=0` 时不保存 checkpoint，适用于纯 smoke；正数时只按明确的 save interval 保存。
- `main.py` 用 `try/finally` 管理 Runner；训练正常返回或异常时都清理 Runner 和 Ray，避免训练主体已经结束但 worker handle/actor cleanup 让进程长时间挂住。
- 这部分解决的是结束阶段挂起、无意保存大优化器 checkpoint 和 Ray 资源残留，不是 log-prob 数值 mismatch 的直接根因，但对“smoke 正常退出”和“之后启动唯一全量任务”是必要的运行时修复。

#### 8.3.5 增加可选的 CoLT KV-cache activation checkpoint 路径

文件：`transformers-4.57.0/src/transformers/models/qwen3_vl/modeling_qwen3_vl.py`

为后续尝试原始长上下文 `4096/512`，新增了 opt-in 的 functional KV-cache checkpoint 路径：

- `_colt_activation_checkpointing_enabled()` 读取 `COLT_ACTIVATION_CHECKPOINTING=1`；
- `_set_colt_cache_layer()` 在不原地改写 autograd tensor 的前提下替换 cache layer；
- `_checkpoint_colt_decoder_layer()` 将旧 K/V 作为 checkpoint 输入、将新 K/V 作为 checkpoint 输出；
- 只有在 `self.training`、环境开关开启且存在 `past_key_values` 时启用；普通推理和当前默认训练路径不受影响；
- 小型 CPU Qwen text model 的 prefill、cached step、loss、cache 和 gradient 对照均得到 exact match。

### 8.6 GPU 可见性问题的专项结论

用户曾观察到某次输出中像是没有 GPU。针对这一点做了物理层、驱动层、框架层和进程层交叉检查：

```bash
nvidia-smi -L
nvidia-smi --query-gpu=index,pci.bus_id,uuid,name,memory.total,memory.used,utilization.gpu --format=csv,noheader

/data/nvme0/lkl/conda/envs/colt-easyr1/bin/python -c \
  'import torch; print(torch.cuda.is_available(), torch.cuda.device_count())'

/data/nvme0/lkl/conda/envs/colt-easyr1/bin/ray status --address='192.168.1.184:24925'
```

结果是：

- 物理层有 8 个 PCI A100 设备，8 个 `/dev/nvidia0..7` 节点；
- `/proc/driver/nvidia/gpus` 有 8 个条目，全部 `GPU Excluded: No`；
- `nvidia-smi -L` 列出 8 张 A100，UUID 与 PCI bus id 一一对应；
- PyTorch `cuda_available=True`、`device_count=8`；
- Ray `8.0/8.0 GPU`，没有 pending resource demand；
- 当前 Ray worker 实际打开 `/dev/nvidia0..7`；
- 当前检查没有发现 NVRM、Xid、ECC 或 PCI 掉卡错误。

因此，当前证据不能支持“GPU 从主机消失”这个判断。更可能的混淆来源有：

1. **逻辑可见性与物理存在性不同**：`CUDA_VISIBLE_DEVICES=7` 时 PyTorch 进程只能看到 1 个逻辑设备，但 `nvidia-smi -L` 仍能列出物理 8 卡。
2. **资源被全量任务占满**：当前 Ray 已经保留 8 张卡；此时另一个训练任务可能 pending 或启动失败，表现像“没有可用 GPU”，但物理卡仍然存在。
3. **OOM 被误读成掉卡**：`4096/512` 长上下文任务是 CUDA OOM，不是 GPU 掉线；OOM 后训练 worker 会退出，但驱动仍可正常枚举 GPU。
4. **CLI 环境不同**：系统 shell 中 `ray` 不在 PATH，直接执行会得到 `ray: command not found`；必须使用 `colt-easyr1` 环境中的 Ray 路径。这个错误与 GPU 是否存在是两件事。

当前直接启动的 RL 命令显式设置了 `CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7`，并通过 Ray/PyTorch/nvidia-smi 交叉验证，不能归因于错误的 GPU mask。历史上某一瞬间的空输出没有同步的内核日志可供还原，因此不对那个瞬时事件做超过证据的断言。

另一个需要保留的工程风险是：`scripts/lkl_8gpu/commands/rl.sh` 的 `rl train` 分支目前主要做 GPU CSV 格式检查并设置 `CUDA_VISIBLE_DEVICES`，没有像 SFT `train`/`eval` 分支那样完整调用 `validate_gpu_profile` 和 selected-GPU idle preflight。它不是本次当前任务 GPU 消失的证据，但后续应补成启动前的物理 GPU 校验，避免把非法 GPU id、被其他任务占用或环境错误误认为训练框架问题。

### 8.7 长上下文 OOM 的真实边界

本轮还做了真实 8 GPU、图像数据、`max_prompt_length=4096`、`max_response_length=512` 的 1-step 尝试，并额外设置 `freeze_vision_tower=true`。结果在第一次 actor `loss.backward()` 附近仍然 OOM：

- GPU 总容量约 `79.33 GiB`；
- PyTorch 已分配约 `76.40` 到 `76.56 GiB`；
- reserved but unallocated 约 `1.23` 到 `1.24 GiB`；
- 剩余显存只有约 `18` 到 `95 MiB`；
- 单次失败尝试还需要约 `96 MiB`，另一次旧配置需要约 `370 MiB`。

日志：`logs/rl/colt_rl_image_longctx_1step_freezevision_20260809.log`、`logs/rl/colt_rl_parity_final_20260809.log`。

这组数字表明主要问题是长序列 activation/working memory 预算不足，而不是单纯 allocator fragmentation，也不是 GPU 丢失。当前全量任务因此明确使用 `512/64`，其含义是：

```text
全量 image-only manifest + 当前可运行长度上限
!= 原始 4096/512 长上下文配置的完整复现
```

要回到 `4096/512`，至少还需要在真实 8 GPU 上验证 functional KV-cache checkpoint、视觉塔/激活保存策略、microbatch 和可能的序列分片组合；在这些验证完成前，不应把当前全量任务报告成原始长上下文正式训练。

长上下文失败中的 NCCL warning 是 barrier 时 rank-to-GPU mapping 尚未显式确认的 warning，当前没有证据表明它导致 OOM；OOM 的直接堆栈仍然落在 actor backward 显存申请失败处。当前 512/64 全量任务连续多个 step 通过 parity 并持续运行，也不支持把该 warning 当成当前主因。

### 11.2 三个提速尝试及结论

#### A. 直接使用 latent generation 返回的 token log-prob：回退

`latent_reasoning_generate` 的 q=1 KV-cache 解码路径已经能够返回 token log-prob，但它与 actor 使用的 q=64 teacher-forced response forward 不是同一条数值路径。真实 8-GPU smoke 在 step 1 的 parity 差为 `0.265606`，远超 `0.05` 容差。因此不能把 generation 内部 log-prob 直接当作训练 old log-prob；该临时代码已完整回退，当前仍使用逐样本 teacher-forced scoring。

#### B. rollout scoring 和 actor experience 同时改为 batch=2：回退

该尝试在 scoring 侧按 B=2 计算，并把 actor experience 改为 B=2，但真实 smoke 在 step 1 的 parity 差为 `0.24901`。原因不是 batch 数字本身，而是 `ray_trainer.py::_balance_batch` 会按有效 token 长度重新排列样本；rollout scoring 的 B=2 分组和 actor 侧重排后的 B=2 分组不相同。当前 Qwen3-VL CoLT latent + FlashAttention 路径对 batch shape 不完全不变，不能只“对齐 batch 大小”而忽略样本分组。该尝试已回退。

#### C. FSDP `no_sync()` 梯度累积：回退且确认会 OOM

曾对除最后一个 update microbatch 外的反向传播包裹 `FSDP.no_sync()`，以减少每个 microbatch 的 gradient reduce-scatter。step 1 parity 仍为 `2.4959444999694824e-06`，但 step 2 在 backward 的 FSDP pre-backward unshard 处 OOM：

```text
GPU 0: 79.33 GiB total, 254.81 MiB free
PyTorch allocated: 74.13 GiB
PyTorch reserved but unallocated: 3.30 GiB
additional requested: approximately 370 MiB
```

该临时代码已回退，当前 actor update 仍使用 microbatch=1、每个 microbatch 正常同步的路径。

### 11.3 OOM 是否因为没有 offload 到 CPU

不是。当前 OOM 的直接对象是 GPU 上的 FSDP 参数/梯度/反向临时 all-gather 峰值，而不是 optimizer state 是否占用了 CPU。当前 actor 的有效 update batch 是：

```text
configured actor.global_batch_size = 16
rollout.n = 4
world_size = 8
global_batch_size_per_device = 16 * 4 / 8 = 8
micro_batch_size_per_device_for_update = 1
```

所以每个 rank 每次 update 要累积 8 个 microbatch。普通 FSDP FULL_SHARD 路径会在每次反向后做梯度同步/分片，GPU 上保留 shard；`no_sync()` 则会延迟这些同步，并在最终同步前积累更大的、未分片的梯度。与此同时，后续 FSDP backward 还需要临时 all-gather 当前层参数。两者叠加就解释了“step 1 能跑、step 2 在参数 unshard 时只差几百 MiB 便 OOM”。

仓库的检查位于 `EasyR1/verl/workers/fsdp_workers.py`，它拒绝：

```text
enable_cpu_offload = true
and global_batch_size_per_device != micro_batch_size_per_device_for_update
```

这不是为了禁止利用 1 TB CPU 内存而写的任意限制。PyTorch FSDP 文档明确说明：CPU offload 下不能在 `no_sync()` 之外进行梯度累积，因为 FSDP 可能使用“新 reduce 后的梯度”覆盖已有梯度，结果不再是期望的 microbatch 梯度和；文档还明确说明，`no_sync()` 内的梯度不会在最终同步前 offload 到 CPU，而是会积累在 GPU，从而增加显存使用。参见 [PyTorch FSDP 文档](https://docs.pytorch.org/docs/stable/fsdp.html) 的 `no_sync()`、`CPUOffload` 和 limitations 部分。

因此直接删除该检查有两种坏结果：

1. 保持现有 `loss.backward()` 循环：CPU offload 可能使每个 microbatch 的梯度被覆盖，训练更新语义错误；
2. 同时改成 `no_sync()`：梯度在最终同步前仍留在 GPU，无法利用那 1 TB CPU 内存，并会复现本轮观测到的 OOM。

理论上可以另写“每个 microbatch 正常同步后，将 sharded CPU gradient 拷贝到独立 CPU accumulator，再清空 FSDP grad，最后恢复 accumulator 做 optimizer step”的实现，但它需要严格处理 FSDP flat/original parameter 映射、reduce scaling、zero_grad 和 dtype，并会为每个 microbatch 引入同步及 GPU↔CPU 拷贝。它是显存 containment 方案，不是当前“提高吞吐”的方案；在 8 张 A100 上很可能比现有 GPU-resident FSDP 更慢，所以本轮没有把未经验证的实现推入训练主路径。

`offload_optimizer=true` 也不能解决这个 OOM：EasyR1 的实现是在 update 前后搬运 Adam state，不能搬运 activation、当前 backward 的参数 all-gather 或 no-sync 梯度；而且会增加每次 update 的 H2D/D2H 流量。当前显存峰值约 `76.3 GiB`、正常 microbatch=1 路径不 OOM，因此优先优化 rollout，而不是改变训练语义。

### 11.4 已落地的安全提速：同一 prompt 的 n=4 generation batching

本轮新增 `worker.rollout.generation_batch_size`：

- 默认值为 `1`，保留旧行为和便于回退；
- 当前 CoLT YAML 设置为 `4`，恰好覆盖 GRPO 的 `n=4`；
- 每个原始 prompt 的 4 个采样在一次 `latent_reasoning_generate` batch 中生成；
- prompt token、attention mask、position ids 和同一图像的 multimodal tensors 按 batch 复制/拼接；
- rollout teacher-forced scoring 仍然逐样本；
- actor experience 和 actor update 仍然是 microbatch=1；
- `_generate_one()` 保留为 batch=1 wrapper，`n=1` validation 自动退化为 batch=1。

这条优化没有把 generation q=1 的 log-prob 偷换成训练 old log-prob，也没有扩大 actor 的 batch shape；因此 parity 仍由原有逐样本 scoring/actor recomputation 契约保护。EOS 后的 token 继续由已有 `response_mask` 屏蔽，训练有效 token 语义不变。

此前同一安全路径的另一次 smoke 中，第 2 步测得 `27.132 s`；差异主要来自 batch 中实际 prompt/response 长度和第一次运行的 kernel/cache 状态。因此不应只用最乐观的 `27.1 s/step` 估算全量。以最终 smoke 的 `32.3–35.0 s/step` 作为更保守的当前基线，周期性每 100 步一次约 6 s 的审计只增加约 `0.06 s/step` 的平均开销，审计本身不是主瓶颈。

这里的 `mfu_actor` 不是 `nvidia-smi` 的 GPU utilization，也不是端到端 MFU，而是 EasyR1 内置 `FlopsCounter` 的 actor-update 代理值：按 Qwen3-VL 的文本配置、当前有效 token 数和 actor update 时间估算 FLOPs，再除以 A100 约 `312 TFLOP/s` 和 8 卡规模。它不包括 rollout generation、rollout teacher-forcing、old/ref/reward、Ray 调度和等待时间，且对视觉塔和 latent 专用路径不是完整 FLOP 建模。因此 `2.7–3.3%` 已足以证明 actor 更新阶段没有接近算力上限，但不能把它直接当成严格的整机 MFU。

此前在 live profiling 期间额外观测到约 `44%` 的 SM utilization、约 `16%` 的显存带宽利用率和约 `178 W/400 W` 的单卡功耗；这些都与“GPU 没有打满”一致。当前 smoke 结束后的 `0%` 是空闲状态，不应与运行期间指标混淆。

按最终 smoke 的阶段分解，step 1 的 `34.962 s` 中约 `14.084 s`（40%）花在 rollout generation 加逐样本 logprob 计算，约 `5.970 s`（17%）是 old 审计，约 `14.898 s`（43%）是 actor update；step 2 删除 old 重算后，gen 和 actor update 仍各占约一半。这说明复用 old logprob 已解决了一个明显的重复 forward，但剩余瓶颈在 rollout 侧的逐样本 teacher-forcing 和 actor 侧的 B1 FSDP update，而不是数据读取或 checkpoint。

#### 11.9.3 是不是数据太多

数据量是总时长的重要乘数，但不是当前单步低算力利用率的根因。原始 JSON 包含 `189,645` 条记录；开启 `filter_overlong_prompts=true` 后，训练 dataloader 日志为 `8442` 个 batch，`rollout_batch_size=16` 且 `drop_last=true`，所以本轮每 epoch 至少有 `8442 × 16 = 135,072` 个有效 prompt slot，末尾不足一个 batch 的样本被丢弃。每个 prompt 采样 `n=4`，因此全量大约会产生 `135,072 × 4 = 540,288` 条 trajectory/sample。

如果保持现有数据和算法语义，最终 smoke 基线对应的理论纯 step 时间约为：

```text
8442 steps × 32.3–35.0 s/step = 75.8–82.0 h = 3.16–3.42 天
```

还要加初始化、周期 checkpoint、I/O、长度波动和偶发 Ray 同步，因此正式全量应按约 `3.3–3.6 天` 规划；此前最乐观的 `27.1 s/step` 也需要约 `63.6 h`，仍然超过两天。

两天目标的硬条件是：

```text
48 h / 8442 steps = 20.47 s/step 或更快
```

相对最终 smoke 的约 `33.6 s/step` 平均值，需要约 `1.64×` 加速；如果不改变每步算法，只靠减少数据，则最多运行约 `5,137` steps，即保留约 `60.8%` 的当前有效 prompt slot，至少需要减少约 `39.2%` 的有效训练数据/steps。按最乐观的 `27.1 s/step` 计算也只能跑约 `6,369` steps，仍需减少约 `24.6%`。这类做法会改变数据覆盖和训练预算，只能称为“两天内的缩短实验”，不能称为原始全量任务等价完成。

#### 11.9.4 失败优化实验为何不能直接采用

本轮在保留 parity gate 的前提下测试了以下候选路径，均已从正式代码清理：

- generation-time token logprob：q=1 的 8-GPU smoke parity 最大误差约 `0.375172`；此前 q=4 约 `0.265606`。因此 latent generation 内部缓存的 logprob 与 actor teacher-forced logprob 不是当前实现下的同一数值路径。
- rollout scoring B2 + actor B2：不做 group-aware reorder 时 parity 约 `0.362934`；加入 group-aware reorder 后仍约 `0.207095`。问题不只是 GRPO `n=4` 样本被 dispatch 打散，而是 Qwen3-VL latent/FlashAttention 路径对 batch shape 仍不具备数值不变性。
- actor update B2：某次 parity 通过，但 step 1/2 分别约 `29.4/38.0 s`，update 时间从约 `9.0 s` 波动到约 `18.5 s`，没有形成可复现的吞吐收益，故没有启用。
- fused cross-entropy：parity 仍通过（约 `3.8e-6`），但 step 2 约 `33.1 s`，没有优于原始 `log_softmax + gather`，所以已恢复原实现。

这些结果说明“必须 B1”不是 latent reasoning 在数学上必然要求的结论，而是当前 vendored Qwen3-VL CoLT 实现、FlashAttention mask/position-id/视觉输入组织以及 FSDP dispatch 的联合行为约束。只要没有先把 batch-shape invariance 修到 logits/logprob 层，就不能通过调大 microbatch 换取正确的加速。

#### 11.9.5 要在两天内完成，最值得做的路线

当前不建议直接重启全量；下一次优化应按以下优先级建立小规模 parity/性能闭环：

1. **优先修 batch-shape invariance。** 对同一个固定 image/prompt/response，逐层比较 B1、B2、B4 的 latent hidden states、attention mask、position ids、视觉特征和 response logits，重点检查 latent hidden generation 是否错误共享 batch 状态，以及 FlashAttention varlen/padding 是否把无效 token 或不同样本的视觉长度带入计算。目标是 B2/B4 与 B1 的 response logprob 最大误差回到现有 `1e-5` 量级以内。
2. **修好后再提高 scoring/actor microbatch。** 目标至少让 4 个 rollout sample 的 teacher-forcing 在一个合法的 packed/varlen forward 中完成，并让 actor experience/update 使用 B2 或 B4；每一步都必须同时通过固定样本 parity、两步 8-GPU smoke 和显存峰值检查。
3. **若单卡路径仍无法并行，考虑资源解耦/流水化。** 将 rollout 和 actor 分配到不同 GPU 资源池并重叠生成与更新，或实现独立样本 packed scoring；这会改变当前 hybrid-engine 的资源布局，必须单独设计和验证，不能仅改一个 batch size。
4. **只有接受实验语义变化时才减少数据或 latent 计算量。** 例如限制 `max_steps` 到约 `5100`、减少 `n` 或 `num_hidden_generations`、降低 response 上限，都可能进入两天，但会改变训练预算、GRPO 方差或 CoLT latent 能力，不能作为“等价优化”默认写入正式配置。

因此当前准确结论是：安全路径已经从约 `35–36 s/step` 降到约 `32–35 s/step`，并彻底移除了 steady-state old-logprob 重算；但距离两天所需的 `20.47 s/step` 仍差约 `1.6×`，GPU 也没有打满。真正的高收益瓶颈仍是 latent 路径的 batch-shape 数值不变性和由此被迫采用的 B1 rollout/actor 计算，而不是单纯的数据加载速度。全量任务保持停止，等待下一轮经过 parity gate 的 batch-invariance 优化。

## 11.10 2026-08-09：继续压缩 RL 吞吐的实测结果

### 11.10.1 本轮目标与判定标准

本轮没有重启 8442-step 全量任务，而是在停止全量任务、确认 8 张 A100 空闲后继续做真实 8-GPU image smoke。所有候选优化均要求同时满足：

1. rollout/actor teacher-forced logprob parity 最大误差不超过 `0.05`，优先保持现有约 `1e-6` 量级；
2. 至少完成 2-step smoke，不能只看单次 kernel warm-up；
3. 不增加正常路径的显存峰值到 OOM 边界；
4. 不把减少 `n`、latent steps、训练数据或 response 上限误报为等价的算力优化。

### 11.10.2 通过的正式优化：跨 prompt generation batch=2

原正式路径已经把同一 prompt 的 `n=4` continuation 放入一次生成 batch，但每个 rollout worker 仍按 prompt 逐行调用。当前 `data.rollout_batch_size=16` 在 8 个 rollout worker 上通常每个 worker 处理约 2 个 prompt，因此新增：

```yaml
worker:
  rollout:
    generation_batch_size: 4
    generation_prompt_batch_size: 2
```

实现语义如下：两个不同 prompt 的各 4 个 continuation 组成 B=8 的 generation forward；每个 prompt 的输入、位置和图像数据按 `repeat_interleave` 对齐，生成结果仍按原 prompt-major 顺序还原。rollout logprob 没有使用 generation 内部的 q=1 token logprob，仍在单样本 teacher-forced 路径中重新计算。

为减少 B=8 generation 中重复的 prompt/latent prefill，又加入了可选的 latent prefix cache：不同 prompt 的前缀先按 B=2 计算，再按每个 prompt 的 4 个 continuation 复制 KV cache；response 自回归仍按 B=8 执行。这个 cache 只用于无梯度 generation，不进入 actor update 或 old-logprob 的 parity 契约。

### 11.10.3 通过的同语义计算削减：动态 response cropping

数据的 `max_response_length=64` 是 padding 上限，而 smoke 中实际 response 平均约 20–25 token。actor/rollout 的 CoLT response forward 过去一直把右侧 padding 位置也送入模型，最后才用 `response_mask` 忽略。

当前实现按 microbatch 内最长有效 response 截断输入，只计算有效 response 前缀，并在返回 logprob 时右侧补零回原始 `[batch, 64]` 形状。它不改变有效 response token 的 labels、position ids、mask 或梯度路径。动态 cropping 已在 8-GPU smoke 中通过 parity；但在当前 prompt/latent prefill 占主导的 workload 中，端到端收益不大，因此不能单独把它当作两天目标的主要来源。

### 11.10.4 最终 steady-state smoke

最终 formal YAML 使用 `generation_prompt_batch_size=2`，只用 CLI 指定真实数据、模型路径和 2-step smoke 输出目录；`rollout_logprob_audit_interval` 保持正式默认值 `100`。日志：

```text

```

结果：

| step | step time | gen | old | actor update | actor MFU | parity | old 是否复用 | max reserved |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 29.000 s | 9.019 s | 5.819 s | 14.151 s | 2.9% | `1.997e-6` | 否 | 69.95 GiB |
| 2 | 27.168 s | 8.188 s | 约 0 s | 13.572 s | 3.3% | 未 audit | 是 | 76.29 GiB |

随后使用 `rollout_logprob_audit_interval=1` 的严格 2-step smoke 复核了更新后 parity：


这里 step 2 的额外约 5.5 s 是强制 old-logprob audit，不代表 steady state。正式运行每 100 步才做一次，平均摊销约 `0.06 s/step`。相对于此前安全路径 `32.3–35.0 s/step`，当前 steady-state 约 `27.2 s/step`；考虑长度波动，应按 `27–30 s/step` 规划，而不是按单次最优值承诺。

### 11.10.5 仍未达到两天：重新估算

8442 steps 在 `27.168 s/step` 下的纯 step 时间约为：

```text
8442 × 27.168 s = 229,353 s = 63.7 h = 2.65 天
```

加入每 100 步一次 audit、初始化、Ray 同步、checkpoint 和样本长度波动后，当前正式任务应按约 `2.7–3.0 天` 规划，仍没有达到两天。48 小时要求：

```text
48 h / 8442 steps = 20.47 s/step
```

因此仍需要约 `1.33×` 的额外稳定加速。当前 MFU 仍只有约 `2.9–3.3%`，它是 EasyR1 actor update 的 FLOP 代理值，不是完整端到端 MFU；结合此前 live profiling 的约 44% SM、约 16% 显存带宽和约 178/400 W 功耗，A100 依旧没有打满。瓶颈仍然是：

```text
逐样本 CoLT teacher-forced scoring + B1 FSDP actor update
```

而不是 reward、advantage、数据读取或 checkpoint。

### 11.10.6 未采用的候选与证据

- rollout response scoring B=2/B=4：在缓存 latent prefix 之后，B=2/B=4 response forward 仍分别出现约 `0.177742/0.14025` 的 parity 误差；因此最终代码不再暴露 rollout logprob batch 配置，继续固定 B1 scoring。
- actor update microbatch=2：通过某些 parity gate，但真实 step/update 时间波动明显；加共同左 padding 裁剪和长度排序后仍没有稳定优于 B1，正式配置继续为 `1`。
- `generation_prompt_batch_size=3`：单步可运行，但由于当前 dispatch 每 worker 通常只有约 2 个 prompt，没有获得进一步 generation 收益。
- `rollout_batch_size=24`、`actor.global_batch_size=24`：真实 1-step 结果为 `49.373 s`，其中 gen `15.227 s`、old `8.398 s`、update `20.497 s`；按处理样本数折算后总 wall-clock 反而劣于 batch16，未采用。
- `freeze_vision_tower=true`：显存峰值下降约 0.5–1 GiB，但 step/update 没有实质下降；由于它还改变可训练参数集合，未作为速度优化写入 RL formal YAML。
- FSDP `forward_prefetch=true`：真实 smoke 无稳定收益，已恢复 `false`。
- FSDP `use_orig_params=false`：真实 smoke 的 rollout/actor parity 直接达到约 `0.23513`，因此保留 `true`。

本轮结论是：两天以内不能在保持当前 `n=4`、`num_hidden_generations=3`、8442 steps、B1 actor update 和 parity 契约的前提下仅靠小修小补实现。若必须严格压到两天，仍需要接受至少一种实验语义或资源布局变化，例如减少训练 steps/数据、减少 latent generations、减少 `n`、使用更多 GPU，或把 rollout 与 actor 解耦并流水化；这些不能直接标记为等价提速。

## 12. 2026-08-10：latent reasoning + RL 框架调研、Monet/vLLM 先例与 CoLT 高吞吐路线

### 12.1 调研动机、问题边界与证据口径

第 11 章的实测已经证明，当前低吞吐不是单一数据加载问题，而是两个系统瓶颈叠加：

1. rollout 使用本项目手写的 `CoLTTransformersRollout`，虽然已经实现跨 prompt generation batching 和 latent prefix cache，但仍缺少 vLLM/SGLang 这类推理引擎的 continuous batching、成熟的 KV-cache 调度和请求级并发；
2. rollout teacher-forced scoring 与 actor update 为了满足训推 log-prob parity，目前仍被限制在 microbatch `1`，使 8 张 A100 上的 actor MFU 只有约 `2.9%–3.3%`。

本节重点回答四个问题：

1. 其他 latent reasoning + RL 工作实际使用了什么训练框架和 rollout 引擎；
2. vLLM 是否从原理上不能支持 continuous latent reasoning；
3. 是否存在“多模态 latent reasoning + EasyR1 + vLLM”的直接工程先例；
4. 对当前 CoLT 来说，什么路线最有希望同时保持 parity 和提升吞吐。

本节严格区分四类结论：

- **论文事实**：论文正文明确报告的方法、实验设置或结果；
- **官方代码事实**：官方仓库、配置或训练脚本可以直接验证的实现；
- **本项目事实**：由当前 CoLT 代码、日志和 8-GPU smoke 直接验证；
- **工程推断**：根据上述证据推导的 CoLT 迁移方案，尚不能当作已实现或已验证结果。

尤其需要避免两个错误等价：

```text
“使用 latent reasoning” != “数学上必须 batch=1”
“论文称训练高效”       != “GPU MFU 高或 wall-clock 吞吐高”
```

### 12.2 论文与官方实现的框架全景

| 工作 | 状态 | Latent 形式 | RL/训练框架 | rollout/推理引擎 | 可验证的规模或配置 | 对 CoLT 的直接价值 |
|---|---|---|---|---|---|---|
| Monet | CVPR 2026，已接收 | 多模态 decoder hidden state 递归回灌 | EasyR1/verl | **定制 vLLM V1 runner** | 官方 RL 脚本使用 8 GPU、rollout batch 64、`n=8`、`max_num_seqs=128` | **目前最接近 CoLT 的直接工程先例** |
| RLTT | 2026 arXiv 预印本 | LoopLM 每个 visible token 前的多次内部 loop | verl + 定制训练路径 | 标准配置使用 vLLM | 论文报告 4×H200、prompt batch 32、每题 8 rollouts | 证明 looped latent model 可接入 verl/vLLM，但完整 loop loss 不是原生 GRPO 即插即用 |

| SLPO | 2026 arXiv 预印本 | MC-dropout 构造连续 transition surrogate likelihood | 自定义 `LatentSLPOTrainer`、TRL/Accelerate | 无 vLLM | 首批公开实现以 GPT-2 COCONUT/CODI 为主，16 GB 以上 GPU | 解决 continuous latent policy likelihood，但系统路径不适合直接替代当前多模态 EasyR1 |
| CoLaR | arXiv 预印本/官方代码 | 概率式 latent head、动态压缩因子 | 自定义 PyTorch/Lightning 风格框架 | 未见 vLLM/SGLang RL rollout | 官方 README 给出训练 batch 256；已有调研记录 RL 使用 LoRA | 算法迁移价值大于吞吐工程价值 |
| LTC | 2026 arXiv 预印本 | 固定 latent thought 后多次采样答案 | GRPO-style on-policy RL | 论文未充分披露 | 主设定 `K=2` thoughts、每个 thought `M=4` answers | 证明同一 latent context 下 answer replication 有助于估计 utility，但没有提供可复用的高吞吐框架 |
| Latent-GRPO / Latent-SFT | 2026 arXiv 预印本 | 受约束的 vocabulary-space latent exploration | Transformers、DeepSpeed、PEFT | 官方仓库有定制 SGLang 快速评测 | 公开代码重点是训练与评测，不是完整 SGLang RL rollout 闭环 | 证明修改 SGLang 支持 latent 推理可行，但改变 latent 表示会改变 CoLT 方法语义 |
| HyRea | ICLR 2026 | continuous token reasoning + RL | 论文描述自定义训练 | 官方仓库称代码受公司服务器限制 | 无足够公开工程证据 | 可作算法相关工作，不能据此选择训练引擎 |

这张表呈现出一个重要规律：

- 多数 latent reasoning + RL 工作仍使用 Transformers、TRL、Lightning 或项目自定义 trainer，原因是 continuous latent action、停止动作、递归 hidden state 和中间状态 loss 都不是普通 token-level RL 接口；
- 这类实现适合验证算法，但一般没有证明 production-grade rollout 吞吐；
- **Monet 和 RLTT 是少数明确把 latent/looped reasoning 接入 verl/vLLM 的公开先例；其中 Monet 与“多模态 Qwen-VL + EasyR1 + continuous latent embedding”最接近当前 CoLT。**

### 12.3 Monet：与当前 CoLT 最接近的直接先例

**论文**：Qixun Wang et al., *Monet: Reasoning in Latent Visual Space Beyond Images and Language*，CVPR 2026。

**论文**：<https://arxiv.org/html/2511.21395>

**官方实现**：<https://github.com/NOVAglow646/Monet>

#### 12.3.1 为什么 Monet 是关键证据

Monet 同时满足此前其他论文没有同时满足的四个条件：

1. 模型是多模态 Qwen2.5-VL-7B，而不是纯文本 GPT-2/Huginn；
2. 中间推理是 continuous latent embedding，而不是普通可见 CoT token；
3. RL 基于 EasyR1/verl；
4. rollout 和推理使用修改后的 vLLM。

其官方 README 明确说明，为支持 latent reasoning，项目分别修改了：

- SFT 阶段的 Transformers Qwen2.5-VL；
- RL 阶段的 Transformers Qwen2.5-VL；
- RL rollout 使用的 vLLM model/runner；
- 离线评测使用的 vLLM model/runner。

这直接反驳了“vLLM 从原理上无法支持 latent reasoning”的强表述。更准确的结论是：

> 标准、未修改的 vLLM 不能直接执行 CoLT 的 latent recurrence；经过模型与 runner 定制后，vLLM 可以维护请求级 latent 状态并执行 continuous latent decoding。

#### 12.3.2 Monet 的 runner 如何执行 latent reasoning

Monet 的 `monet_gpu_model_runner.py` 在请求级维护 latent 状态。其核心流程可以概括为：

```text
正常 token decode
  -> 模型采样到 latent-start token
  -> runner 读取最后一层 hidden state
  -> 将该 hidden state 记录为下一 decode step 的 pending embedding
  -> 下一步覆盖对应请求行的 inputs_embeds
  -> 重复固定 latent_size 次
  -> 强制/记录 latent-end 状态
  -> 恢复普通 visible-token decode
```

关键点不是简单地在请求开始时传一次 `inputs_embeds`，而是 runner 每个 decode step 都可以：

- 判断某个 request 当前处于普通文本阶段还是 latent 阶段；
- 从前一步 forward 中取得该 request 的 hidden state；
- 将它作为该 request 下一位置的输入 embedding；
- 在同一个 continuous batch 中允许不同请求处于不同阶段；
- 继续使用 vLLM 的 KV cache 和调度框架。

这与 CoLT 的递归 hidden-state 回灌在系统接口上高度相似。

官方 RL 环境固定了：

```text

transformers==4.51.3
vllm==0.8.5
```

官方 `vlpo_train.sh` 使用：

```text
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
N_GPUS_PER_NODE=8

```


#### 12.3.4 Monet 证明了什么、没有证明什么

Monet 已证明：

- 多模态 latent reasoning 可以在 EasyR1 中训练；
- vLLM runner 可以按 request 维护 latent decoding 状态；
- latent rollout 不必数学上固定为 batch `1`；
- 官方实现至少能够配置 rollout batch `64` 和 `n=8`。

Monet 尚未公开证明：

- 训练期间的端到端 MFU；
- 每 step wall-clock 时间或总训练时长；
- 修改前后 vLLM 的严格吞吐对比；
- Transformers actor 与 vLLM rollout 的逐 token log-prob parity；
- 其大 batch 配置在所有长度分布下都能达到高 GPU 利用率。

因此，Monet 是“架构可行性证据”和“高并发配置证据”，不是 CoLT 可以直接获得某个固定加速倍数的证据。

#### 12.3.5 不能直接复制 Monet runner 的原因

Monet 与当前 CoLT 存在以下语义差异：

| 维度 | Monet | 当前 CoLT fixed-v2 |
|---|---|---|
| latent 触发 | 模型采样特殊 latent-start token | 图文 prompt 后固定进入 latent 阶段 |
| latent transition | 最后一层 hidden 直接作为下一输入 | `prj(last_hidden)` 作为下一输入 |
| latent 位置 | 可与 visible token 交错 | 回答前固定执行 K 步 |
| latent 长度 | 由 `LATENT_SIZE` 和特殊 token 状态机控制 | 当前正式 RL 固定 `K=3` |
| 回答前输入 | latent 段结束后恢复文本解码 | K 次 transition 后还有 final latent input，再生成首个可见 token |
| RL 目标 | VLPO，包含 Monet 专用 latent 概率建模 | 当前为 visible-answer Outcome-GRPO |
| 自定义参数 | Monet Qwen2.5-VL latent 路径 | CoLT `prj`、可能的 `alpha`/gate/K-conditioning 等 |

当前 CoLT 的 vLLM 实现必须精确复现：

```text
PREFILL
  -> LATENT_TRANSITION_1
  -> ...
  -> LATENT_TRANSITION_K
  -> FINAL_LATENT_INPUT
  -> FIRST_VISIBLE_TOKEN
  -> VISIBLE_DECODE
```

也就是说，回答前不是简单插入 K 个 dummy token，而是存在 **K 次递归 transition 加一次 final latent input，共 K+1 个连续 embedding 输入位置**。该位置语义、KV-cache 长度、`position_ids/cache_position` 必须与当前 Transformers 实现完全一致。

此外，Monet 通过 monkeypatch 整个 `vllm.v1.worker.gpu_model_runner` 接入，版本耦合较强。CoLT 可以借鉴其状态机和 embedding override 设计，但不应未经审计直接复制整个 runner。

### 12.4 RLTT：verl/vLLM 可承载 looped reasoning，但完整 loss 仍需定制

**论文**：Jonathan Williams and Esin Tureci, *Prioritize the Process, Not Just the Outcome: Rewarding Latent Thought Trajectories Improves Reasoning in Looped Language Models*，arXiv:2602.10520，2026 预印本。

**论文**：<https://arxiv.org/html/2602.10520>

**官方实现**：<https://github.com/jonwill8/RLTT>

RLTT 使用 Ouro/LoopLM：在预测每个 visible token 前，模型内部执行多次 loop，每个 loop 都能产生针对同一个 next token 的 distribution。论文实现使用 verl 和 vLLM，报告的主要训练设置包括：

```text
4 × H200 140GB
Ouro-2.6B
prompt batch=32
8 rollouts per prompt
max generation length=2048
full-parameter update
约 140 training steps
```

RLTT 对本项目的系统意义是：

- verl/vLLM 的 orchestration 并不局限于普通一次前向的 decoder；
- loop-aware 模型可以在 vLLM rollout 下生成 trajectory；
- actor 侧可以为中间 loop 增加定制 loss。

但 RLTT 不能被误解为“原生 verl 已完整支持任意 latent trajectory loss”。其官方实现区分标准 verl/vLLM 路径和定制 RLTT loss 路径；普通 GRPO 路径只能自然优化最终 loop，完整中间-loop supervision 仍需要定制 trainer/model forward。

RLTT 与 CoLT 的差别也很大：

- Ouro 的每个内部 loop 天然针对同一个 next visible token；
- CoLT 的 K 个 latent transition 全部发生在整段答案之前；
- CoLT-RLTT 若要获得每个 latent prefix 对整段 sampled answer 的 distribution，需要从每个 prefix teacher-force replay answer，或从每个 prefix 重新采样 continuation；
- 因此前者的 cache snapshot 和计算放大比 Ouro loop loss 更复杂。

结论是：RLTT 支持“保留 verl 并扩展 latent-aware loss”的总体方向，但不能直接解决当前 CoLT rollout executor 和 B1 parity 问题。

### 12.5 LSRL：单卡低成本不等于高吞吐 rollout

**论文**：Hangliang Ren, *LSRL: Process-Supervised GRPO on Latent Recurrent States Improves Mathematical Reasoning*，Findings of EMNLP 2025，已同行评审。

**论文与元数据**：<https://aclanthology.org/2025.findings-emnlp.669/>

LSRL 对 3.5B Huginn 的每个 recurrent depth 解码中间答案，再使用 GPT-4.1-nano 给 latent depth 序列提供过程监督。论文报告：

- 使用 LoRA；
- 单张 NVIDIA L40S；
- 仅 500 个 GSM8K 训练问题；
- 相对 depth-8 supervised baseline，GSM8K 提升 4.27 个百分点，MathQA 提升 2.06 个百分点。

LSRL 的“efficient route”主要来自小数据、LoRA 和单卡可训练性，不代表：

- rollout 使用了高吞吐引擎；
- GPU MFU 高；
- 每个 latent depth 的额外解码成本低；
- 可以按当前 189,645 条多模态数据规模直接扩展。

对 CoLT 来说，LSRL 最适合作为 external process-grader 强基线。CoLT 已有 latent-to-CoT decoder，因此比完全不可解码的 latent model 更容易建立该基线；但它不是解决当前 rollout 系统瓶颈的框架方案。

### 12.6 HRPO、SLPO 与 CoLaR：为什么多数 latent RL 仍停留在自定义 Transformers 路径

#### 12.6.1 HRPO

**论文**：Yue et al., *Hybrid Latent Reasoning via Reinforcement Learning*，NeurIPS 2025。

**论文**：<https://openreview.net/forum?id=LjtgTpWH71>

**官方实现**：<https://github.com/Yueeeeeeee/HRPO>

HRPO 官方脚本使用 Unsloth `FastLanguageModel`、TRL `GRPOTrainer`，并明确设置：

```python
fast_inference = False
use_vllm = False
```

默认脚本给出 `per_device_train_batch_size=8`、group size `4`。这说明 latent reasoning 并不天然要求 batch `1`，但也说明 HRPO 的公开工程目标不是把递归 latent rollout 接进 vLLM。迁移到 HRPO 框架会丢失当前 EasyR1 的多模态数据、FSDP、reward 和 Ray orchestration 优势，不能作为首选提速方案。

#### 12.6.2 SLPO

**论文**：Runyang You et al., *SLPO: Scaling Latent Reasoning via a Surrogate Policy*，arXiv:2607.19691，2026 预印本。

**论文**：<https://arxiv.org/abs/2607.19691>

**官方实现**：<https://github.com/ModalityDance/SLPO>

SLPO 的核心难题是 continuous latent transition 没有类似 token action 的精确离散 likelihood。它通过多次 MC-dropout forward 估计 Gaussian surrogate transition density，同时训练 stop head，并将 latent likelihood、answer likelihood 和 stopping likelihood 共同乘以 trajectory advantage。

官方代码使用：

```text
PyTorch
Transformers 4.52
TRL 0.19
Accelerate 1.7
custom LatentSLPOTrainer
vendored RLOO trainer components
```

首批公开主线是 GPT-2 COCONUT/CODI，最低约 16 GB VRAM，较大模型建议多卡；未见 vLLM rollout。该路线增加 MC-dropout、多 latent trajectory 和 adaptive stopping，会进一步提高当前 CoLT 的 rollout 计算量，因此适合算法 ablation，不适合用来直接解决当前吞吐瓶颈。

#### 12.6.3 CoLaR

**论文**：*Think Silently, Think Fast: Dynamic Latent Compression of LLM Reasoning Chains*，arXiv:2505.16552。

**论文**：<https://arxiv.org/abs/2505.16552>

**官方实现**：<https://github.com/xiaomi-research/colar>

CoLaR 使用概率式 latent head、随机 compression factor 和 RL 探索不同压缩路径。官方仓库是项目自定义 PyTorch/Lightning 风格框架，未提供 vLLM/SGLang RL rollout 证据。

论文和代码中的“推理链长度缩短”不能直接等价为 wall-clock 或 GPU 吞吐提升，因为：

- latent transition 本身仍有完整模型 forward 成本；
- compression factor `c` 与 CoLT latent depth `K` 不是同一个量；
- 训练阶段还包含随机 latent sampling 和 RL group rollout；
- 没有公开 MFU、tokens/s 或同硬件端到端对比。

CoLaR 对本项目的价值仍是概率 latent head、动态预算和 RL 探索机制，而不是可直接复用的高吞吐系统。

### 12.7 LTC、Latent-GRPO 与 HyRea：信用分配和 latent action 的证据，不是 rollout engine 答案

#### 12.7.1 LTC

**论文**：Xuyang Zhao et al., *Latent Thought Credit: Multi-Answer Credit Assignment for Latent Reasoning*，arXiv:2608.01593，2026 预印本。

**论文**：<https://arxiv.org/html/2608.01593>

LTC 对每个 sampled latent thought 固定 post-thought context，再采样多份答案，用平均 reward 降低 answer-decoder 噪声：

```text
K=2 latent thoughts
M=4 answers per thought
total rollout budget=8
```

论文披露了 Qwen2.5-3B/7B 的算法结果，但没有充分披露可复用的训练引擎、GPU wall-clock、MFU 或 rollout backend。它支持当前 `n>1` 和 prefix downstream utility 的方法动机，但若直接增加同一 latent prefix 下的 answer replication，反而会进一步放大 rollout 系统成本。因此需要先有高效 runner，再考虑 LTC-style estimator。

#### 12.7.2 Latent-GRPO / Latent-SFT

**论文**：Jingcheng Deng et al., *Latent-GRPO: Group Relative Policy Optimization for Latent Reasoning*，arXiv:2604.27998，2026 预印本。

**论文**：<https://arxiv.org/html/2604.27998>

**官方实现**：<https://github.com/DJC-GO-SOLO/Latent-SFT>

公开训练路径主要基于 Transformers、PyTorch、DeepSpeed、PEFT 和 FlashAttention；仓库还提供修改后的 SGLang 包用于快速评测。其工程价值在于证明：高吞吐引擎可以通过修改 sampler、embedding/model 实现支持特殊 latent token/embedding 行为。

但它采用 vocabulary-space/soft-token latent，与 CoLT 当前连续 hidden-state recurrence 不同。若把 CoLT 改造成 vocabulary-space latent，确实可能更容易复用标准 token scheduler，但这会改变：

- latent 表示空间；
- SFT checkpoint 契约；
- latent transition 目标；
- 论文方法本身。

因此它只能作为独立算法 ablation，不能作为“保持 CoLT 语义不变的系统优化”。

#### 12.7.3 HyRea

**论文**：Zhao et al., *Learning to Reason over Continuous Tokens with Reinforcement Learning*，ICLR 2026。

**论文**：<https://openreview.net/forum?id=lebJ6wz1vj>

**官方仓库**：<https://github.com/zhaoyiran924/HyRea>

HyRea 是 continuous-token RL 的重要算法证据，但其公开仓库说明代码受公司服务器限制，当前没有足够的公开 runner、训练配置、权重同步和吞吐证据。因此不能把它列为当前工程框架选型依据。

### 12.8 vLLM 的真实能力边界

#### 12.8.1 标准 vLLM 已具备的能力

vLLM 官方支持：

- 为未原生支持的模型注册 out-of-tree model/plugin；
- 多模态模型自定义注册；
- `EmbedsPrompt` 形式的静态 prompt embedding；
- continuous batching、paged KV cache、prefix caching、chunked prefill；
- RL 场景下的模型权重更新与常见 verl 集成。

官方文档：

- 模型注册：<https://docs.vllm.ai/en/stable/contributing/model/registration/>
- Prompt embeddings：<https://docs.vllm.ai/en/stable/features/prompt_embeds/>

#### 12.8.2 标准能力仍不足以直接执行 CoLT

`EmbedsPrompt` 接受的是预先计算好的 `[seq_len, hidden_size]` 输入。CoLT 的 latent embedding 无法在请求开始前一次性算完，因为：

```text
h_1 depends on prompt forward
h_2 depends on h_1 and the updated KV cache
...
h_K depends on h_{K-1}
```

因此 CoLT 需要的不只是 custom model registration，而是 decode loop/runner 级扩展：

1. 每个 request 保存 `latent_step` 和执行阶段；
2. forward 后取得指定请求的 last hidden state；
3. 执行 CoLT `prj` 和相关 conditioning；
4. 下一步覆盖该请求的 input embedding；
5. 正确更新 position 和 KV cache；
6. latent 内部占位不泄漏到最终 response token/mask；
7. actor 更新后同步所有 CoLT 自定义权重。

#### 12.8.3 A100 不能依赖 vLLM 官方 batch invariance 功能

vLLM 的 batch-invariance 功能用于让输出独立于 batch composition/order，但官方文档指出该功能要求 compute capability 至少 `9.0`，主要面向 H100/H200/B100/B200，且仍处于 beta：

<https://docs.vllm.ai/en/v0.12.0/features/batch_invariance/>

当前 A100 是 SM80，因此不能把该功能作为 B1/B2 parity 的解决方案。即使未来换 H100，它也只能约束 vLLM 自身数值路径，不能自动修复当前 Transformers actor 在 B1/B2 下的 batch-shape 差异。

### 12.9 为什么当前 batch=1 不是 latent reasoning 的数学必然

当前已观测到：

```text
rollout response scoring B2 parity error ~= 0.177742
rollout response scoring B4 parity error ~= 0.14025
generation-time q=1 logprob parity error ~= 0.27–0.38
安全 B1 teacher-forced parity ~= 2e-6
```

这些证据只能支持：

> 当前 vendored Qwen3-VL/CoLT/FlashAttention/FSDP 的特定批处理路径不满足所需 parity。

它们不能支持：

> 任意 continuous latent reasoning 方法都必须 batch=1。

反证包括：

- Monet 官方 rollout 配置使用 batch 64、`n=8`；
- HRPO 官方训练脚本的 per-device batch 默认是 8；
- SLPO/CoLaR 同样以 group/batch 方式训练 latent trajectories。

当前 CoLT 更可能存在 batch-shape implementation bug 或不一致路径，例如：

- left padding/共同裁剪后 `position_ids` 或 `cache_position` 不一致；
- 不同图像 token 长度下 multimodal merge 和 attention mask 不一致；
- latent prefix cache 在 repeat/reorder 后与 prompt/sample mapping 不一致；
- FlashAttention varlen 与单样本路径使用了不同 mask/数值路径；
- response teacher forcing 的 logits alignment 在 batch padding 下偏移；
- 某个 model/runner 临时状态错误地跨 batch 共享；
- FSDP dispatch、padding-free 或 packing 改变了有效张量形状。

在逐层 trace 定位前，不能把误差归因于“浮点误差较大”，也不能通过放宽 `0.05` gate 掩盖问题。

### 12.10 vLLM 单点优化仍不足以稳定进入两天

以第 11.10.4 节 steady-state step 2 为基线：

```text
total             = 27.168 s
rollout generation = 8.188 s
actor update       = 13.572 s
other              = 5.408 s
training steps     = 8442
```

只加速 generation 的理论估算：

| generation 加速 | 新 generation | 预计 step | 8442 steps 纯 step 时间 |
|---:|---:|---:|---:|
| 1× | 8.188 s | 27.168 s | 63.7 h |
| 2× | 4.094 s | 23.074 s | 54.1 h |
| 4× | 2.047 s | 21.027 s | 49.3 h |
| 无限快/归零 | 0 s | 18.980 s | 44.5 h |

这意味着：

- vLLM 即使让 rollout generation 达到 4 倍加速，纯 step 时间仍约 49.3 小时，尚未计入初始化、audit、checkpoint 和长度波动；
- 即使假设 generation 完全免费，44.5 小时也几乎没有留给任何系统开销；
- 因此 vLLM 是高价值优化，但不是稳定两天目标的充分条件。

为了给非 step 开销留出余量，推荐的工程目标是：

```text
rollout generation: 8.2 s  -> 3–4 s
actor update:       13.6 s -> 9–10 s
total step:         27.2 s -> 18.5–19.0 s
```

这要求 rollout 引擎改造与 actor batch-shape invariance 修复并行，而不能依次等待。

### 12.11 推荐架构：保留 EasyR1/verl，只替换 latent rollout executor

当前不推荐迁移到 HRPO、SLPO、CoLaR 的 trainer，也不推荐第一步就把整个 EasyR1 rollout backend 换成 SGLang。推荐结构如下：

```text
EasyR1 / verl
├── data / reward / GRPO orchestration       保留
├── FSDP actor / ref                         保留并继续修 batch invariance
├── current Transformers CoLT model          作为正确性 oracle
└── CoLT-vLLM rollout executor               新增
    ├── multimodal prefill
    ├── per-request latent state machine
    ├── prj / K-conditioning / gate
    ├── K transitions + final latent input
    ├── visible decode
    └── custom weight synchronization
```

第一阶段仅让 vLLM 负责 generation：

- rollout 用 vLLM 采样 response token；
- old log-prob 仍由参数更新前的 Transformers actor 对同一 response teacher-force 重算；
- rollout 与 actor 的 tokenization、multimodal inputs、K 和 response mask 必须固定；
- 只有 parity 通过后才考虑直接复用 vLLM generation logprob。

这样做的 trade-off 是第一阶段仍保留一次 Transformers scoring，但可以先验证 vLLM latent generation 的正确性，并把最复杂的“sampling logprob 是否等价”与“latent runner 是否等价”拆成两个独立问题。

### 12.12 CoLT-vLLM feasibility spike 的最小实现范围

#### 12.12.1 版本矩阵先行

当前本项目环境是：

```text
PyTorch 2.6.0 + CUDA 12.4
vendored Transformers 4.57.0
EasyR1 本地分支
Qwen3-VL CoLT custom model
```

当前 `EasyR1/requirements.txt` 声明 `vllm>=0.8.0`，但为 CoLT 单独构建的 `requirements-colt.txt` 没有安装 vLLM。Monet RL 则固定在：

```text
PyTorch 2.6.0
Transformers 4.51.3
vLLM 0.8.5
Qwen2.5-VL custom model
```

因此不能直接把 Monet 依赖装进现有正式环境。第一步必须建立兼容矩阵，至少确认：

- vLLM 版本是否原生支持当前 Qwen3-VL；
- vLLM 需要的 Transformers 版本是否与 vendored 4.57.0 冲突；
- FlashAttention、PyTorch、CUDA ABI 是否一致；
- EasyR1 当前 weight-update 接口对应 vLLM V0 还是 V1；
- out-of-tree registration 是否足以承载 Qwen3-VL multimodal processor；
- 是否必须像 Monet 一样 patch `gpu_model_runner`。

#### 12.12.2 第一版只实现固定 K=3

为了限制范围，第一版应明确不实现：

- adaptive K；
- stochastic gate；
- per-prefix snapshots；
- step-level reward；
- latent sampling likelihood；
- prefix cache；
- CUDA Graph。

只实现当前 formal RL 已使用的 deterministic fixed-v2、`K=3`、visible-answer Outcome-GRPO。只有这一语义通过 parity 后，再扩展 latent policy 功能。

#### 12.12.3 第一版 runner 的必要状态

每个 request 至少需要：

```text
phase: PREFILL | LATENT | FINAL_LATENT | TEXT | FINISHED
latent_step: 0..K
K
pending_inputs_embeds
multimodal request mapping
KV-cache block mapping
visible response token ids
model-weight version
```

runner 必须保证：

- latent 内部占位不会进入用户可见 response；
- latent 位置不会被 reward parser 当作 answer token；
- latent 位置不会错误进入 PPO response mask；
- 每个 request 的 image grid、rope delta 和 cache position 不串行；
- request reorder/preemption/resume 后 latent state 仍与正确请求对应；
- 权重更新后旧 latent cache 不跨版本复用。

#### 12.12.4 自定义权重同步

标准 Qwen3-VL 权重同步不足以覆盖 CoLT。至少需要测试：

- `prj` 参数；
- latent scale/`alpha`；
- gate 或 K-conditioning（若当前 checkpoint 含有）；
- 所有新增 buffer；
- tied embedding/lm-head 关系；
- FSDP shard 到 vLLM 参数名映射。

不能只验证“参数数量相同”或“load_weights 没报错”。建议在 actor 完成一次人工参数扰动后，对指定参数 checksum 和固定输入 logits 做前后对比，确认 vLLM 确实加载了新权重。

### 12.13 parity 与性能验收矩阵

CoLT-vLLM 不能以“能生成合理答案”为验收标准。建议固定 16 条真实 image-only RL 样本，建立以下矩阵：

| 维度 | 测试值 |
|---|---|
| batch | B1、B2、B4，随后再扩大 |
| latent depth | K=0、K=3 |
| decode | greedy、固定 seed sampling |
| image shape | 同尺寸、不同尺寸/不同视觉 token 长度 |
| response | 固定 teacher-forced response、真实 sampled response |
| 权重状态 | 初始权重、一次 actor update 后 |

需要比较：

1. multimodal prefill 后最后 hidden state；
2. 每个 latent transition 的 `prj(hidden)`；
3. 每一步 KV-cache 长度和 cache position；
4. first visible token logits；
5. 完整生成 token IDs；
6. Transformers actor 对相同 response 的逐 token log-prob；
7. rollout/actor response mask 和有效 token 数；
8. 权重更新前后 vLLM 参数版本。

通过标准：

```text
硬 gate: max valid-token logprob diff <= 0.05
目标值:  尽量保持当前约 1e-5 或更低数量级
greedy:  token IDs 完全一致
K fingerprint: K=0 与 K=3 路径可被明确区分
```

性能报告必须分阶段，而不能只给总 step：

```text
multimodal prefill time
latent transition time
visible decode time
teacher-forced scoring time
actor update time
end-to-end step time
tokens/s/GPU
SM utilization
memory bandwidth utilization
power
actor MFU proxy
```

### 12.14 性能功能的恢复顺序

在第一版 parity 通过前，推荐主动关闭：

```text
CUDA Graph
prefix caching
chunked prefill
speculative decoding
复杂 request preemption/resume
```

随后按以下顺序逐项恢复，每开启一项都重新跑完整 parity matrix：

1. continuous batching；
2. 提高 `max_num_seqs`；
3. chunked prefill；
4. request preemption/resume；
5. prefix caching；
6. CUDA Graph；
7. 直接复用 generation log-prob。

prefix caching 风险尤其高。cache key 除普通 prompt token 外，还必须覆盖或隔离：

- 图像内容及 multimodal processor 输出；
- K；
- latent method/config；
- actor 权重版本；
- 会影响 latent transition 的所有自定义参数。

如果 cache key 没有表达这些状态，可能产生“吞吐更快但 behavior policy 错误”的静默故障。

### 12.15 actor batch invariance 仍必须并行修复

即使 vLLM rollout 成功，actor update 仍约占 `13.6 s/step`。因此另一路必须继续使用固定样本 golden trace 定位 B1/B2/B4 差异：

```text
processor outputs
-> multimodal merge
-> attention mask / position ids / rope delta
-> prefill hidden
-> latent step 1..K hidden
-> final latent input
-> response logits
-> valid-token logprob
```

建议先在单 GPU、无 FSDP、`eval()`、greedy、固定 BF16/FP32 条件下复现，再逐层增加：

1. FlashAttention；
2. 不同图像长度；
3. left padding；
4. FSDP；
5. backward/update。

只有先找到第一个发生偏差的张量，才能判断是实现 bug、kernel 数值路径还是数据组织问题。当前证据不支持继续盲试更大的 actor microbatch。

### 12.16 备选路线及其边界

#### 12.16.1 SGLang

SGLang 是合理备选，因为 Latent-SFT 已展示对 sampler、embedding 和模型实现进行 latent-aware 修改的先例，且 verl 支持 SGLang rollout。但迁移将涉及：

- EasyR1 rollout backend；
- Qwen3-VL multimodal model port；
- CoLT latent runner；
- actor-to-SGLang weight sync；
- parity 和 cache 生命周期。

在已有 Monet/EasyR1/vLLM 直接先例的情况下，SGLang 应作为 vLLM runner spike 被证明过度侵入或版本不可兼容后的备选，而不是第一选择。

#### 12.16.2 异步 rollout/训练框架

verl fully-async、AReaL、slime 等框架可以通过 rollout/actor 资源解耦和流水化提高硬件利用率，但它们并不原生理解 CoLT latent recurrence。使用这些框架前仍然需要一个 latent-aware vLLM/SGLang executor。

此外，完全异步训练还会引入 stale policy/off-policy 问题，并通常需要独立 rollout GPU 池。当前只有 8 张 A100 且 actor 已占满显存，因此它是资源布局变化，不是零成本软件开关。

#### 12.16.3 LoRA

LSRL、HRPO、CoLaR 等许多工作依赖 LoRA，从而允许更大的 batch 和更低训练显存。LoRA 可能显著改善 actor microbatch，但会把当前 full-parameter Outcome-GRPO 改成 parameter-efficient RL，影响：

- 可训练参数集合；
- 与当前 full-RL baseline 的公平性；
- 最终能力上限；
- checkpoint 合并与部署。

因此 LoRA 可以作为独立效率 baseline，不能被描述成与当前全参数训练完全等价的系统优化。

#### 12.16.4 改成 vocabulary-space latent

Latent-GRPO/Latent-SFT 的 soft-token/vocabulary-space latent 更容易复用 token-centric scheduler，但会改变 CoLT 的核心表示和 SFT 训练契约。该方向只能作为方法变体，不应混入“保持 CoLT 不变的 rollout 加速”。

### 12.17 最终判断与下一步优先级

本轮调研后的准确判断是：

1. **用户关于 rollout engine 是主要瓶颈之一的判断成立。** 当前手写 Transformers rollout 没有复用成熟的 continuous batching 和 KV 调度；
2. **“vLLM 没有原生集成 CoLT”成立，但“vLLM 不能做 latent reasoning”不成立。** Monet 已提供多模态 EasyR1 + 定制 vLLM 的直接反例；
3. **当前 batch=1 是实现约束，不是 latent reasoning 的数学要求。** 其他 latent RL 工作的大 batch 配置和 Monet 的 request-level latent runner 均支持这一点；
4. **只替换 rollout engine 仍不足以稳定进入两天。** 4× generation 加速的理论纯 step 时间仍约 49.3 小时；
5. **最佳路线不是更换 RL 框架，而是保留 EasyR1/verl，参考 Monet 为 CoLT 实现专用 vLLM runner，同时继续修 actor batch-shape invariance。**

推荐优先级调整为：

```text
P0-A: actor B1/B2/B4 golden trace，定位首个不一致张量
P0-B: CoLT-vLLM 版本兼容与 fixed-K=3 feasibility spike
P1:   generation-only vLLM parity 闭环
P2:   continuous batching 和 max_num_seqs 吞吐测试
P3:   actor microbatch B2/B4 parity + 8-GPU smoke
P4:   chunked prefill / prefix cache / CUDA Graph
P5:   SGLang 或异步资源解耦备选
```

在任何新全量任务启动前，必须至少满足：

```text
真实图像 parity <= 0.05
固定 greedy token IDs 一致
更新后权重同步测试通过
2-step 真实 8-GPU smoke 通过
steady-state <= 20.47 s/step；若要给系统开销留余量，目标 <= 19 s/step
```

## 13. 20260810 Monet-style GRPO 组内 prefix 复用：parity 保持与两天目标突破

### 13.1 根因结论

本轮先修复了一个独立正确性缺陷：CoLT 在混合长度、右 padding 的 batch 中曾使用 `hidden_states[:, -1, :]` 初始化 latent，短样本会取到 padding hidden。现在训练与推理统一通过 attention mask 提取每行最后一个有效 token。

随后把 parity 诊断从“同一个 B=2 forward 重复两次”扩展为真正的 B=2 对 B=1 逐行对照。结果显示：

| 路径 | batch-shape 最大 logprob 差异 |
|---|---:|
| BF16 + FlashAttention 2，不同 prompt | `0.09615`，失败 |
| BF16 + SDPA，不同 prompt | `0.12494`，失败 |
| BF16 + eager，不同 prompt | `0.23938`，失败 |
| FP32 + SDPA，不同 prompt | `4.53e-6`，通过 |

逐层 trace 发现差异从 prompt prefill 已经出现，并在 K=3 latent recurrence 中放大。FP32 对照把误差降到 `1e-6` 量级，因此根因不是剩余的 mask/position 错误，而是 BF16 batch-dependent GEMM/attention 数值差异经过 latent recurrence 放大。不能通过放宽 `0.05` 门槛解决。

此外，真实图像 B=1 中 online decode logprob 与 teacher-forcing logprob 仍相差 `0.06448`；因此 generation 内部 q=1/q=4 logprob 仍不能直接代替 actor old logprob。

### 13.2 vLLM 兼容性 spike 与环境恢复

Monet 使用 Torch 2.6、Transformers 4.51.3、vLLM 0.8.5，并整体 monkeypatch Qwen2.5-VL runner。当前 CoLT 是 Qwen3-VL：

- vLLM 0.8.5 与当前 Torch 2.6 匹配，但没有 Qwen3-VL registry；
- vLLM 0.10.x 仍没有所需的 Qwen3-VL executor；
- vLLM 0.11.2 开始包含 Qwen3-VL，但要求 Torch 2.9，和当前 driver/CUDA/已验证环境不是低风险升级；
- 直接把 0.11.2 的 Qwen3-VL executor 回移到 0.8.5 会缺失 attention backend registry 等接口，不是单文件移植。

曾在 `colt-easyr1` 中短暂安装 vLLM 0.8.5 验证 registry，确认不可直接使用后已卸载，并恢复 NumPy、protobuf、numba、llvmlite、Starlette 和 OpenTelemetry 等原版本。最终 CUDA/import 自检通过；`pip check` 只剩本环境此前已有的 `vllm`、`liger-kernel` 元数据缺失，当前 `colt_transformers` 路径不依赖二者。

### 13.3 最终实现：B1 latent prefix + B4 response

没有继续强行让不同 prompt 一起做 BF16 latent recurrence，而是采用 Monet 的 request-state 思路，并利用 GRPO 同一 prompt 有 `n=4` responses 的结构：

1. trainer 按 `uid` 聚合完整 GRPO group，再以组为原子做 8-way 长度均衡；同一组不会被拆到不同 rank；
2. 每卡的 experience/update microbatch 从 1 提升到 4，并断言四行 uid 相同；
3. 每组只对第一行执行一次 image/prompt/K=3 latent prefix，保留完整 autograd 图；
4. 将 latent hidden 与每层 KV cache `repeat_interleave(4)`；repeat 的梯度会汇总回同一个 prefix 图；
5. 四条不同 response 以 B=4 teacher forcing 计算；rollout scoring 与 actor experience/update 使用相同分组、相同裁剪和相同 batch shape；
6. 非完整 group、组大小不等于 `rollout.n`、prompt token/mask 不相同会立即报错，不做静默 fallback。

单 GPU sampled B=4 对照中：普通 B=4 相对逐行 B=1 的误差为 `0.22517`；共享 B1 prefix 后降为 `0.04547`，在原 `0.05` 门槛内通过。该结果同时包含四条不同 sampled responses，不是复制同一答案得到的虚假 parity。

### 13.5 全量配置与时间估计

### 13.6 尚存边界

- 该优化依赖 GRPO 同 prompt 的完整 `n=4` group；online filtering 若产生残缺组会被显式拒绝；
- 当前 image-only manifest 每条样本是一组图像输入；视频和复杂多图样本仍需单独 smoke；
- online generation logprob 与 teacher forcing 仍不是同一路径，不能删除 teacher-forced rollout scoring；
- `4096/512` 长上下文 OOM 问题没有被本轮结果替代；当前结论仍限定于正式 `512/64` 任务。
